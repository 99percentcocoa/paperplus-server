## Notes / deviations from the original plan doc
- Poetry is not installed in this environment; using plain `requirements.txt` + venv per service instead (simpler, no new tooling to install). Revisit if the team wants Poetry later.
- Local dev DB: a separate `paperplus_v2` Postgres database (same local Postgres 14 instance, same `postgres` superuser as the old system) was created — deliberately kept separate from the production `paperpluslive` DB. Credentials live in `api-service/.env` (gitignored).
- Known gotcha hit during setup: SQLModel + Alembic autogenerate emits `sqlmodel.sql.sqltypes.AutoString()` in generated migrations without importing `sqlmodel` — fixed by adding `import sqlmodel` to both `alembic/script.py.mako` (for future migrations) and the generated baseline file.
- Environment flakiness: this sandbox is a resource-constrained, recently-booted WSL2 VM; Postgres connections (even via unix socket) intermittently hung during setup. Not a code issue — resolved by restarting the Postgres cluster. Worth watching for during Phase 3 (memory-hungry ML deps).
- **Architecture correction found while porting Phase 3**: the old system's `scan_image()` resolves template name partly via a DB lookup (`db.worksheets.get_worksheet_json`) as a fallback. Since vision-service has no DB access by design, this fallback is dropped — template is now inferred purely from row-tag format (`omr_v2` -> `basic_omr`, else `regular`), with an optional `template_hint` override in the request contract for api-service to force a choice. Updated `shared/contracts.py` accordingly (removed the caller-supplied `TemplateSpec`, which wrongly assumed the template was known before the image was even scanned).
- **Grading/checked-image scope**: vision-service returns raw `question_marks` (marked option + confidence per question) only — it does NOT compute correctness or draw the annotated "checked" image, since both need the answer key (DB-only, api-service's job). This is Phase 4 scope.
- **Model naming quirk ported faithfully**: the old system's *actually active* bubble-marking model is `blur_model_optimized.tflite` — the `bubble_model_quantized.tflite` call site is commented out in `services/inference.py`. Wired vision-service the same way; `bubble_model_path` setting is kept for a possible future switch.
- PaddleOCR (heavy, ~500MB+) deferred per decision — `app/vision/ocr.py` has an `OCRProvider` protocol with `StubOCRProvider` (always returns "") wired in at startup, and a ready-to-enable `PaddleOCRProvider` implementing the same variant-fallback strategy as the old code.

Note that means `/webhook`, `/api/admin/*` (including the write endpoints), and `/files/*` are all open, and compose also publishes `8000` and Postgres `5432` on the host -- simplest later hardening is nginx basic-auth in front of `/admin` + `/api/admin` and dropping those host `ports:`. Static HTML/JS (no build step, no new Python deps) in `api-service/app/static/admin/`; JSON API in `app/routes/admin.py` (`/api/admin/*`); correction logic in `app/services/corrections.py`.
  - **Why new storage was needed**: the vision result (`question_marks` + ROI boxes, `page_no`, `question_paper_code`) and file locations were only logged, then discarded, and `ScanReview` had no image reference -- a failed scan could never be corrected without re-running vision. New `scans` table (migration `8a5fea39ade8`): one row per received image, success or failure, holding upload/dewarped/checked paths, `from_number`, and the full `vision_result` JSONB; `scan_reviews.scan_id` links to it. `scans.worksheet_id` deliberately has no FK (an unrecognized worksheet id is one of the failures it records) and `correlation_id` is a plain index, not unique.
  - **Refactor**: the post-grading tail of `handle_incoming_image` is now `persist_graded_scan()` (merge page -> state transitions -> attempts -> mastery/level -> graded), shared by the WhatsApp flow and the dashboard's failed-scan resolution. `insert_attempts`/`affected_skills` made public.
  - **Views**: Overview (KPIs, recent submissions, open failed scans, 30s refresh), Submissions list/detail (scan image beside a per-question grid with answer dropdowns, live correct/incorrect preview), Failed scans list, Failed-scan detail (image, student search, worksheet/question-paper-code override with answer-key reload, per-question answers, "Save & create submission" or Dismiss). A "your name" box (localStorage) is recorded as `corrected_by`.
  - **Corrections** (`correct_submission`, `resolve_review`): validate options against the question's real option labels, recompute `is_correct` and the score **server-side** from the answer key (the old dashboard's correct endpoint trusted a client-sent score and never rebuilt attempts/mastery), replace `attempts`, refresh mastery/level for the changed skills, regenerate the annotated image from the stored dewarped image + ROI boxes, and write an audit `ScanReview` (original vs corrected answers/score, `corrected_by`, `corrected_at`) -- the first use of those long-unused columns. Failed scans whose vision call itself failed (no `vision_result`) can only be dismissed.
  - **Known limits**: resolving a failed scan for a student who already has a submission for that worksheet overwrites/merges it exactly like a WhatsApp rescan would (the UI does not warn yet -- worth adding); mastery recompute appends a `MasteryHistory` row per correction and level changes never roll back; `Submission.submitted_at` isn't bumped on rescan/merge so "recent submissions" ordering reflects first submission; pre-v2/migrated submissions have no scans so their detail page shows answers without images; a correction regenerates the checked image for every scan linked to the submission, including superseded scans of the same page.
  - `GET /files/{kind}/{filename}` now serves `uploads|dewarped|debug|checked` (traversal-guarded, media type from extension; old `/files/checked/...` URLs unchanged).

Open `/admin` in a browser and click through it before relying on it.
  - **Two follow-up fixes to the dashboard (2026-09-19)**, both found by the user testing rescans of `0151_1.jpeg`: (1) rescanning the same student+worksheet overwrites the submission row but never bumped `submitted_at`, so the recent-submissions list showed nothing new -- `_create_or_overwrite_submission` now sets `submitted_at` on every rescan. (2) Failed-scan entries were never closed once the underlying problem was fixed: reviews for "student not registered" / "worksheet not inserted" stayed open with their old time forever even after the same scan later graded fine. New `close_superseded_reviews()` (`submission_service.py`) runs after every successful grade and after `resolve_review`: it closes open reviews with the same detected roll number AND same worksheet (decoded, not admin-overridden) AND same page (when both known), marks them `corrected` with `corrected_by="system (later scan graded)"` and links the submission. Deliberately conservative: a review with a stored scan whose worksheet couldn't be decoded is left open, a different page is left open, and other students' failures are untouched; legacy reviews with no stored scan and no worksheet match on roll number alone. Resolving a review also closes its open duplicates (same image resent). 76 tests pass; verified live -- rescanning `0151_1.jpeg` closed the two stale Sep 17 reviews (#71, #79) and linked them to submission 205.
- **Dashboard monitoring/alerting + restart policies (2026-09-21)**: `restart: unless-stopped` was already on all four compose services (commit `4567ee7`) -- nothing to add there (note it restarts *crashed/exited* containers only; a hung-but-running container isn't restarted without healthchecks + an autoheal, not built). New `GET /api/admin/monitoring` (`app/services/monitoring.py`) returns dependency health (DB ping, vision-service `/health` ping with latency), scan throughput (1h/24h, graded vs failed, failure rate, vision-failure count, time since last scan), review backlog (open count + oldest age), and storage-volume usage, plus a list of alerts with `warning`/`critical` severity and an overall `status`. Alert rules are pure functions of the snapshot (unit-tested without a DB) with thresholds in `Settings` (`ALERT_*` env vars, documented in `infra/.env.example`): vision/DB unreachable = critical; failure rate (with a minimum sample so 1-of-2 doesn't alarm), vision failures in the last hour, review backlog size/age, no scans for N hours (a webhook-broken signal; off if 0) = warning; disk warn/critical. The endpoint still answers when the DB is down (reports critical, skips the DB-derived sections), and error strings are deliberately generic (no URLs/DSNs) since the admin API is unauthenticated. UI: a "System status" panel at the top of the Overview (status pill, alert banners, stat cards), a status dot in the topbar on every page (refreshed every 60s; also red if the API itself is unreachable), and the Overview now still renders the status panel when the data calls fail. This is dashboard-level alerting only -- nothing pages anyone; point an external uptime monitor at `/api/admin/monitoring` or `/health` for that. 14 new tests (`tests/test_monitoring.py`); 90 api-service tests pass. **Two real bugs caught by checking against the live server/DB rather than trusting the first green test run**: (1) SQLAlchemy stores an explicit Python `None` in a JSONB column as JSON `null`, not SQL `NULL`, so a `vision_result IS NULL` filter never matches real vision-failure scans (the "vision failures" alert would silently never have fired); now matches both forms. (2) Naive `timestamp` columns hold whatever the DB session's TimeZone made of the UTC value written -- this dev Postgres is `Asia/Calcutta`, docker's is UTC -- so labelling them UTC in Python gave "-5.2 hours since last scan"; timestamps are now cast to `timestamptz` in SQL so the DB applies the same interpretation it used on write. The first version of the test asserted `hours_since_last_scan < 1`, which a negative number satisfies -- now bounded on both sides. **The browser UI was still not run** (no JS runtime here; only syntax-checked with a pure-Python parser and the endpoint exercised live) -- click through the Overview first. **Related pre-existing issue, not changed**: `admin.py`'s `_iso()` returns naive ISO strings (no `Z`/offset), which the browser parses as *local* time; that displays correctly only when the DB timezone matches the browser's (true on this dev box, not on the UTC docker Postgres viewed from IST, where submission/scan times would show ~5.5h early).
- **vision-service made fully stateless -- shared image volume removed (2026-09-21)**: `dewarped_image_path` was a hidden cross-service file dependency (vision-service wrote the dewarped page to a shared volume, api-service read it), and the reverse direction existed too (vision-service `cv2.imread`'d an upload path api-service had written), so dropping only the dewarped path would have left the shared volume in place. Investigating "do we ever need the dewarped image" found it *is* needed by code even though no human needs to see it: `draw_checked_image()` draws the student-facing checked image on it (every ROI box is in dewarped coordinates, so it can't be drawn on the original photo), and the admin "correct an answer" flow redraws from it. Done with the fully-stateless option: `ProcessRequest` is now `{correlation_id, image_b64, template_hint}` and `ProcessingResult` returns `dewarped_image_b64` (base64 JPEG); vision-service decodes with `cv2.imdecode`, encodes with `cv2.imencode`, and writes nothing to disk (its `storage_root` setting, `_save_artifact`, and the unused debug image are gone). `HTTPVisionClient.process(image_path, ...)` keeps its signature (path on *api-service's* disk), base64-encodes the upload itself, and stores the returned dewarped page in api-service's own `storage_root/dewarped/`, exposing it as `result.dewarped_image_path` and clearing the base64 so the blob never lands in `scans.vision_result` -- so `submission_service`, the fakes and nearly all tests are unchanged. A corrupt/unwritable dewarped payload degrades to "no checked image for this scan" rather than failing a scan that already graded. Removed: `scans.debug_path` (migration `35c162409d67` -- run `alembic upgrade head`), the admin viewer's "dewarped" tab, and `dewarped`/`debug` from the served `/files/{kind}` kinds (dewarped pages stay on disk for redrawing but aren't served). `docker-compose.yml` no longer mounts `files_data` into vision-service, which can now run on a different machine. Verified `cv2.imdecode` == `cv2.imread` pixel-for-pixel on all 11 fixtures first (so scan results can't shift), then end-to-end with the real vision-service, real `HTTPVisionClient` and real DB: graded correctly, api-service stored the dewarped page, the checked image came out byte-size-identical to the pre-change one for the same photo, and vision-service's old `files/` dir was untouched. New tests: `tests/test_vision_client.py` (sends base64 and never a path; stores the dewarped page and drops the blob; degrades on a bad payload; missing upload / HTTP errors -> `VisionClientError`), `test_main.py` (invalid/empty/non-image input -> 400; the old `image_path` request -> 422; a real scan returns a decodable dewarped JPEG whose size matches the target and contains every ROI, with `cv2.imwrite` booby-trapped to prove no disk writes). 96 api-service + 48 vision-service tests pass (accuracy suite still 10/10 over the new path). **Not verified**: the docker images were not rebuilt/run here (Docker unreachable in this shell) -- rebuild both images and re-run a scan through the compose stack. **Deploy notes**: breaking wire change, so deploy api-service and vision-service together; old dewarped files already in the `files_data` volume keep working for corrections (their paths are in `scans.dewarped_path`); the local-dev `shared_dev_files/` workaround for a shared `STORAGE_ROOT` is no longer needed by vision-service.
