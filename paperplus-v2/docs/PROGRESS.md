## Notes / deviations from the original plan doc
- Poetry is not installed in this environment; using plain `requirements.txt` + venv per service instead (simpler, no new tooling to install). Revisit if the team wants Poetry later.
- Local dev DB: a separate `paperplus_v2` Postgres database (same local Postgres 14 instance, same `postgres` superuser as the old system) was created — deliberately kept separate from the production `paperpluslive` DB. Credentials live in `api-service/.env` (gitignored).
- Known gotcha hit during setup: SQLModel + Alembic autogenerate emits `sqlmodel.sql.sqltypes.AutoString()` in generated migrations without importing `sqlmodel` — fixed by adding `import sqlmodel` to both `alembic/script.py.mako` (for future migrations) and the generated baseline file.
- Environment flakiness: this sandbox is a resource-constrained, recently-booted WSL2 VM; Postgres connections (even via unix socket) intermittently hung during setup. Not a code issue — resolved by restarting the Postgres cluster. Worth watching for during Phase 3 (memory-hungry ML deps).
- **Architecture correction found while porting Phase 3**: the old system's `scan_image()` resolves template name partly via a DB lookup (`db.worksheets.get_worksheet_json`) as a fallback. Since vision-service has no DB access by design, this fallback is dropped — template is now inferred purely from row-tag format (`omr_v2` -> `basic_omr`, else `regular`), with an optional `template_hint` override in the request contract for api-service to force a choice. Updated `shared/contracts.py` accordingly (removed the caller-supplied `TemplateSpec`, which wrongly assumed the template was known before the image was even scanned).
- **Grading/checked-image scope**: vision-service returns raw `question_marks` (marked option + confidence per question) only — it does NOT compute correctness or draw the annotated "checked" image, since both need the answer key (DB-only, api-service's job). This is Phase 4 scope.
- **Model naming quirk ported faithfully**: the old system's *actually active* bubble-marking model is `blur_model_optimized.tflite` — the `bubble_model_quantized.tflite` call site is commented out in `services/inference.py`. Wired vision-service the same way; `bubble_model_path` setting is kept for a possible future switch.
- PaddleOCR (heavy, ~500MB+) deferred per decision — `app/vision/ocr.py` has an `OCRProvider` protocol with `StubOCRProvider` (always returns "") wired in at startup, and a ready-to-enable `PaddleOCRProvider` implementing the same variant-fallback strategy as the old code.
- **Phase 4 known limitations (deliberate, tracked for follow-up)**:
  - Answer keys are resolved from the new normalized `question_options` table (canonical) with an optional per-variant override from `question_paper_variants` (**DONE** — see below), not the old `omr_answer_sets`/`worksheet_json` blobs. Grading only works once worksheets are seeded via the new schema (Phase 8 migration, not done yet).
  - `question_paper_variants` **simplified and wired into grading**: clarified that `basic_omr` variants (A-F) are fixed per-variant answer keys shared by every printed copy — NOT per-copy shuffled bubbles. Replaced the originally-designed `option_order` JSONB (position-shuffle translation) with a plain `correct_option_label` column (Alembic migration `df221253c582`). `resolve_answer_key(session, worksheet_id, question_paper_code)` now prefers a seeded variant's correct label over the canonical `question_options.is_correct` one, falling back to canonical when no variant row exists for that code. 3 new tests.
  - Multi-page OMR answer merging: **DONE** (Option C, page-aware). See `app/domain/submission_merge.py`. Unlike the old system's hardcoded `worksheet_category == "omr" and question_index > 39` heuristic, this uses the real `worksheet_pages.first_question_index`/`last_question_index` range for whichever page was actually scanned (from vision-service's `page_no`). That page's full expected range always replaces prior data for those indices — gaps are filled as explicit "unanswered" rather than silently carrying forward stale answers from a previous scan of the same page — while other pages' answers from a prior submission are preserved untouched. 5 new tests (4 unit tests on the merge function + 1 full two-page integration test through `handle_incoming_image`).
  - Answer-key resolution **extended with a code-level tier (2026-09-09)**: `question_paper_variants` required a re-seeded answer key per `(worksheet_id, question_paper_code)` pair, but `basic_omr` codes (A-F) mean the same fixed answers on every printed copy regardless of `worksheet_id`. `resolve_answer_key` now also checks the previously-unused `omr_answer_sets` table for a `question_paper_code`-only row (`worksheet_id IS NULL`) between the per-worksheet variant and the canonical fallback. New script `scripts/insert_code_answer_key.py --code D --answer-key A,B,C,...` seeds one key per code, not per worksheet. 2 new tests in `tests/test_grading_variants.py`.
  - Grading with no resolvable answer key anywhere **now refuses to grade instead of silently scoring 0** (2026-09-08) — see `InvalidAnswerKeyError` in CLAUDE.md.
  - Early failures before a `Submission` row exists (vision-service error, unrecognized roll number, unknown worksheet, missing answer key) **DONE (2026-09-09)** — now persisted as `ScanReview` rows (that table's `submission_id`/`student_id`/`worksheet_id` are all nullable for exactly this case; it existed in the baseline schema but was never wired up until now). `vision_failed`/`invalid_student`/`invalid_worksheet` write `status=failed`; `invalid_answer_key` writes `status=needs_review` (a content-seeding gap, not a bad scan) — feeds a future dashboard "failed scans" view. 3 new tests.
  - Checked-image annotation (✔/✘ marks + score badge) **DONE (2026-09-09)** — ported from `services/grading_service.py:check_worksheet` + `services/image_service.py:save_checked`/`make_circle_mark`. Needs both services' data (vision-service's pixel ROI boxes + api-service's post-grading correctness), so `shared/contracts.py`'s `QuestionMark` gained `roi_x1/y1/x2/y2` (vision-service already computed these internally in `get_roi_coordinates`, just wasn't returning them) and api-service draws the annotation itself, in `app/domain/annotation.py`, using PIL against the `dewarped_image_path` vision-service already saves (PIL, not cv2, because ✔/✘ are Unicode glyphs `cv2.putText` can't render — fonts copied from the old repo's `assets/` into `api-service/assets/fonts/`). New `checked_image_path`/`checked_image_url` columns on `Submission` (migration `980422e12355`) make this durable, unlike the old system where the checked image was ephemeral (disk + served URL only, never persisted). New static route `GET /files/checked/{filename}` (`app/routes/files.py`) serves it; `comm_client.send_image()` (already defined, previously unused) sends it over WhatsApp; `app/services/sheets_logging.py` fire-and-forget-posts a matching audit payload to `settings.sheets_logging_url` if configured (no-ops otherwise), porting `services/logging_service.py:log_to_sheet`. 2 new tests (`test_handle_incoming_image_draws_and_sends_checked_image` + a ScanReview NEEDS_REVIEW check appended to the existing no-answer-key test). Verified against a real scan (`setD_page1.jpeg`) — output visually matches the old system's style exactly (green ✔ boxes, red box for the one wrong answer, score-circle badge).
    - Deviation from the old payload: `services/logging_service.py:log_to_sheet` also logged `fileURL` (raw uploaded image) and `debugURL` (vision-service's debug overlay) alongside `checkedURL`, but neither is served over HTTP in v2 yet (only the checked image got a route) — the ported payload only sends `checkedURL` + `sender`/`marked`/`score`/`detectedRollNumber`/`worksheet_id`. Add a `/files/dewarped/{filename}` and `/files/debug/{filename}` route later if full payload parity is wanted.
    - Found and fixed a real local-dev-only bug while verifying this: `vision-service` and `api-service` each resolve `storage_root` (`./files`) relative to their own process's CWD, so when run as separate manual `uvicorn` processes on one machine (not via `docker-compose`, which already mounts a shared `files_data` volume at `/app/files` in both containers), api-service couldn't find the dewarped image vision-service had saved. Fixed for local dev by pointing both services' `.env` `STORAGE_ROOT` at the same absolute directory (`paperplus-v2/shared_dev_files/`, gitignored) — this was latent before now because nothing previously actually opened `dewarped_image_path` from api-service's side.
  - CLI-based worksheet/template *generation* (plan item 4.2: `batch_generate_worksheets.py`, `worksheet_pdf_generator.py`, `worksheet_json_generator.py`) was NOT ported — deliberately deferred; the old standalone scripts remain the only way to author worksheet PDFs/JSON. *Insertion* (plan item 4.3: `bulk_insert_worksheets.py`, `insert_single_worksheet.py`, `import_students_from_csv.py`, `sample_insert_omr_answer_variants.py`) **is now ported** — see the Phase 4 (insertion CLI) entry above.
  - All Phase 4 open items are now closed except the deliberately-deferred worksheet/template generation CLI above. All 41 api-service + 36 vision-service tests pass.
